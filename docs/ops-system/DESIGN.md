# 生产计划 & 出货管理系统 — 设计方案

> 状态：方案草案，待确认
> 分支：`claude/production-plan-wecom-integration-0e470t`
> 最后更新：2026-09-06

---

## 1. 背景与目标

**现状**

| 环节 | 现在怎么做 | 问题 |
|---|---|---|
| 生产计划 | 人工（纸/Excel） | 排产靠经验，进度不透明，交期没预警 |
| 出货单 / 装箱单 | 人工 | 抄写易错，格式不统一，没有留痕 |
| 进销存 + 财务 | **畅捷通**（保留） | 不动它，只做数据衔接 |

**目标**：自研一套轻量生产管理系统，跑通 `订单 → 排产 → 工单 → 报工 → 出货单` 这条链，
和企业微信打通；畅捷通继续管进销存和财务，两边通过单据衔接，**不重复建账**。

**明确不做**（这些是"贵"的来源，小工厂不需要）：
- 完整 APS 高级排程（有限产能自动优化求解）
- 完整 MES（设备联网、SPC、质量追溯全链）
- 财务、成本核算、应收应付 —— 畅捷通已经在做

## 2. 关键约束：从第一天就要为东南亚建厂做准备

客户已明确未来在**东南亚开厂**（官网现有市场：中国 / 泰国 / 越南 / 英文）。
下面四件事**必须一开始就做进架构**，事后补的代价极大（等于重写）：

### 2.1 多站点（multi-site）维度

每一条业务数据都带 `site_id`。将来泰国/越南开厂，**新增一个 site 即可**，
不改表结构、不拆系统、不复制一套代码。

```
site: CN-HQ (中国总部/工厂) → 未来 TH-xxx / VN-xxx
```

每个 site 自带：时区、本位币、默认语言、单据号前缀、通知通道。

> ⚠️ 反例：如果一期只做单工厂、表里不留 `site_id`，将来开第二个厂只能
> 「再部署一套系统」，然后两套数据永远对不上。

### 2.2 时区与币种

- **所有时间戳一律存 UTC**，显示时按当前 site（或当前用户）的时区渲染。
- 中国 UTC+8、泰国 UTC+7、越南 UTC+7 —— 跨时区最容易在**交期、排产日、报工时间**上出错。
- 金额一律 `(amount, currency)` 成对存储，不存裸数字。

### 2.3 通知层必须可插拔 —— 企业微信只是其中一个通道

**这是最容易踩的坑。** 东南亚员工不用企业微信：泰国用 LINE，越南用 Zalo，
其他市场用 WhatsApp（官网现在就是按市场分渠道的）。

所以业务代码里**不出现任何企业微信 API 调用**，只调用统一接口：

```ts
interface Notifier {
  readonly channel: "wecom" | "line" | "zalo" | "whatsapp" | "email";
  send(to: Recipient, msg: LocalizedMessage): Promise<SendResult>;
}

// 业务代码长这样，与通道无关：
await notify(workOrder.owner, { key: "wo.dispatched", params: { no, item, due } });
```

- 消息内容是 **i18n key + 参数**，按收件人语言渲染 —— 中国人收到中文，泰国人收到泰文。
- 站点 → 通道的映射放配置：`CN-HQ → wecom`，将来 `TH-xxx → line`。
- 一期只实现 `wecom` 和 `email` 两个 Notifier，其余留接口。

### 2.4 身份认证同样可插拔

一期：企业微信 OAuth 免登（员工在企业微信里点开就是自己，不用记密码）。
但接口要抽象，东南亚站点将来可能用邮箱/手机号，或 LINE Login：

```ts
interface IdentityProvider { resolve(req: Request): Promise<SessionUser | null>; }
// 一期实现：WecomOAuthProvider、PasswordProvider（备用/管理员）
```

## 3. 多语言方案

### 3.1 界面文案 —— 复用官网现成骨架

官网已有完整 i18n 基础设施，内部系统直接沿用同一套，不另起炉灶：

| 现有资产 | 复用方式 |
|---|---|
| `src/i18n/{en,zh,th,vi}.json` | 新增 `ops.*` 命名空间，四种语言从第一天就建 |
| `scripts/validate-locales.mjs` | 现成的 key 对齐校验（缺 key / 多 key / 空值 / 数组长度不一致），直接覆盖新增文案 |
| `components/LocaleContext.tsx` | 语言上下文与切换逻辑，直接复用 |

语言集与官网一致：**中文 / 英文 / 泰文 / 越南文**。

### 3.2 业务数据的多语言（比界面更关键）

界面翻译只是一半。**数据本身也要多语言**，否则泰国厂看到的物料名还是中文：

- 物料名、客户名、工序名、不良原因等 → 存 `jsonb`：`{"zh":"...","en":"...","th":"..."}`
- 取值规则：**当前语言 → 英文兜底 → 任一非空**，永不显示空白
- 编码类字段（物料编码、单据号）**不翻译**，全站统一

### 3.3 单据的多语言

出货单 / 装箱单要发给东南亚客户，模板必须支持：
- **中英对照**（国内出口常用）
- 或纯英文 / 泰文 / 越南文（按客户所属 site 或客户偏好语言）

单据模板做成数据驱动，不写死中文标签。

## 4. 技术架构

```
┌─────────────────────────────────────────────────────┐
│  Next.js 16 (TypeScript)  —— 与官网同技术栈          │
│                                                     │
│  /ops/*   电脑端后台：排产看板、工单、出货单开单      │
│  /ops/m/* 手机端 H5：企业微信内打开，扫码报工         │
│  /api/ops/*  业务 API + 企业微信回调                 │
└──────────────┬──────────────────────────────────────┘
               │
        ┌──────┴──────┐          ┌─────────────────┐
        │  PostgreSQL │          │  通知层（可插拔）│
        │  (腾讯云)    │          │  企业微信 / 邮件 │
        └─────────────┘          │  → 将来 LINE/Zalo│
                                 └─────────────────┘
               │
        ┌──────┴────────────────────────┐
        │  畅捷通衔接                    │
        │  一期：Excel 导入 / 导出        │
        │  二期：开放平台 API（待确认）    │
        └───────────────────────────────┘
```

**为什么用 Next.js 而不是换栈**：与官网同栈，一套技术、一套构建、一套部署经验，
维护成本最低；服务端渲染对国内网络友好；H5 在企业微信内置浏览器里表现好。

## 5. 数据模型草案

> 每张业务表都带 `site_id`（见 2.1）；所有时间戳 `timestamptz`，存 UTC。

**主数据**

| 表 | 关键字段 | 说明 |
|---|---|---|
| `site` | code, name_i18n, timezone, currency, default_locale, doc_prefix | 工厂/站点 |
| `app_user` | site_id, name, wecom_userid, email, phone, role, locale, active | 用户；`wecom_userid` 可空（东南亚员工没有） |
| `item` | code, name_i18n, spec, uom, category, chanjet_code | 物料/成品；`chanjet_code` 用于对账 |
| `customer` | code, name_i18n, country, contact, default_locale, chanjet_code | 客户；`default_locale` 决定单据语言 |
| `process` | code, name_i18n, seq | 工序（一期可极简） |

**业务单据**

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sales_order` / `_line` | no, customer_id, item_id, qty, due_date, currency | 订单与交期，可从畅捷通导入 |
| `production_plan` | site_id, period_start, period_end, status | 排产周期（周/日看板的载体） |
| `work_order` | no, item_id, qty_planned, qty_done, qty_scrap, planned_start/end, due_date, status, barcode, so_line_id | **工单**，系统核心 |
| `work_report` | work_order_id, operator_id, qty_ok, qty_ng, ng_reason, reported_at, source | **报工**（`source`: wecom_scan / web） |
| `shipment` / `_line` | no, customer_id, ship_date, incoterm, carrier, tracking_no, status | **出货单** |
| `package` / `_line` | shipment_id, box_no, gross_wt, net_wt, dims | **装箱单**（箱与明细多对多） |
| `notification_log` | channel, recipient, template_key, payload, status, sent_at | 通知留痕，便于排查"没收到" |
| `audit_log` | actor, entity, entity_id, action, before, after, at | 谁改了什么，出货/计划变更必须留痕 |

**单据状态**（草案，待按实际流程调整）

```
work_order: 待排产 → 已排产 → 生产中 → 已完工 → 已入库 → 已关闭
shipment:   草稿 → 待审 → 已确认 → 已发货 → 已签收
```

## 6. 企业微信集成

均为成熟公开接口，无技术风险：

| 能力 | 用途 | 接口 |
|---|---|---|
| 自建应用 | 系统载体 | corpid + agentid + secret |
| 网页授权免登 | 员工点开即登录，不建第二套账号 | OAuth2 网页授权 |
| 应用消息推送 | 工单下发、交期预警、出货待确认 | 消息推送（textcard / markdown） |
| 审批 | 计划变更、超期出货 | OA 审批 API + 回调 |
| JS-SDK 扫一扫 | **车间扫工单条码报工** —— 对小工厂最实用 | `wx.scanQRCode` |
| 通讯录同步 | 人员与部门自动对齐 | 通讯录 API（可选） |

> 注意：企业微信回调要求服务器公网可达且响应及时 —— 这是选**国内云**部署的原因之一。

## 7. 畅捷通衔接

**这是全方案唯一的不确定项**，所以一期设计成**不依赖它的 API**：

**一期（不被卡住）**
- 畅捷通导出 商品 / 客户 / 库存 → 系统 Excel 导入（做字段映射 + 校验 + 冲突报告）
- 系统生成出货单 → 导出为畅捷通可导入的销售出库单格式
- 通过 `item.chanjet_code` / `customer.chanjet_code` 做双向对账

**二期（确认后再做）**
- 畅捷通开放平台 API 自动同步
- **前置条件**：确认产品线（好生意 / T+Cloud / T+ 本地版）、版本、以及能否申请到开放平台授权

导入导出层同样抽象成接口，二期接 API 时业务代码不动。

## 8. 代码托管与部署

**GitHub 为唯一源（source of truth），腾讯云为只读镜像。**

```
   开发/协作/PR                自动镜像              部署拉取
GitHub (helloskmodel) ──────────────────────► 腾讯云代码仓库 ──────► 腾讯云服务器
```

- **GitHub**：日常开发、PR、评审、CI 都在这里
- **腾讯云仓库**：只读镜像，**不要在腾讯云侧直接提交**（会被镜像覆盖）；
  作用是让国内部署拉代码不走境外网络，且境外网络异常时仍可发布
- 镜像由 GitHub Actions 自动完成，见 `.github/workflows/mirror-to-tencent.yml`

**部署**
- 国内：腾讯云（轻量服务器/CVM）+ PostgreSQL，员工访问快，企业微信回调稳定
- 东南亚开厂后：可加新加坡节点就近服务（官网图片已用 `ap-singapore` COS），
  数据库按合规要求决定集中还是分区
