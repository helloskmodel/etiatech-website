# 灯泡序列号全链路追溯 — 设计方案

> 状态：方案草案，待确认
> 关联：`docs/ops-system/DESIGN.md`（生产计划 & 出货管理系统）
> 最后更新：2026-09-07

---

## 1. 需求与价值

**要做的事**：每支灯泡有唯一序列号（"身份证"）。进货扫一次、出货扫一次，
从此每支灯泡都能回答：**什么时候生产 → 什么时候入库 → 什么时候出货给谁**。
客户在网站上可以查询。

投放两处：**海外网站**（etiatech.com）+ **手机端**。

**这件事真正值钱的地方，不止是"有记录"：**

| 价值 | 说明 |
|---|---|
| **防伪** | UV 灯泡在东南亚有假货和翻新货。客户扫码即可验证是不是 ETIA 正品供应链出来的——这是**销售武器**，不只是内部管理 |
| **保修自动判定** | 保修从出货日算起。有了链路，"这支还在保吗"由系统回答，不用翻单据吵架 |
| **窜货/串货追踪** | 泰国的货出现在越南客户手里，一扫就知道 |
| **召回定位** | 某批次有问题，一次查询就能列出这批灯泡去了哪些客户 |
| **客户信任** | 客户能自查自己买的每一支灯，这在 B2B 里是明显的专业度信号 |

## 2. 实物标签现状（已核对实物照片，2026-09-07）

**结论先说：灯泡目前没有唯一序列号，主机有。两类物品必须分开处理。**

### 2.1 灯泡（消耗品）—— 只有型号 + 手写批次

Excelitas 灯泡包装盒标签实际内容：

| 项目 | 实际值 | 性质 |
|---|---|---|
| Part Number | `012-64000R` | **型号**，同型号所有灯泡都一样 |
| Lot Number | `28/2026 019` | **批次**，且是**蓝色圆珠笔手写** |
| Lamp Type | 200 W Mercury Arc, INTELLI-LAMP® | 规格 |
| 产地 / 文档号 | MADE IN USA / 916-00071 Rev.3 | — |
| 条码 / 二维码 | **完全没有** | — |

**所以：**

- ❌ **没有唯一序列号** —— Lot 是批次号，一个批次涵盖多支灯泡，不是"身份证"
- ❌ **没有任何机读码** —— 扫不了，一维二维都没有
- ⚠️ **批次号是手写的** —— OCR 不可靠（`0/O`、`1/I`、`8/B`，还有个人笔迹），只能人工录入

> **推论：要做到"每一支灯泡"的追溯，ETIA 必须自己发号、自己贴码。这不再是优化建议，
> 而是唯一可行的路径。**

### 2.2 主机 / 控制器 —— 现成就能扫

S2000-XLA 铭牌上已经有：

| 项目 | 实际值 |
|---|---|
| Model No. | `S2000-XLA` |
| **序列号** | `S2000-XL-A-1560` ← **唯一** |
| **DataMatrix 二维码** | ✅ 铭牌上已印 |
| 滤光片选项 | 320–500 nm（`019-01049R`）勾选 |
| 文档号 | 911-00007R Rev.4 |

**主机不用贴新标签，直接扫现有 DataMatrix 即可。**

> ⚠️ **采购坑**：DataMatrix 是**二维码**，**便宜的一维激光扫码枪读不了**。
> 必须买 **2D 影像式（imager）扫码枪**。这一点买错了整批设备就白买。
>
> ⚠️ 另外要先实扫一支确认 **DataMatrix 里编的到底是什么** —— 可能就是序列号，
> 也可能是原厂内部编码。解析规则要按实扫结果定，不能假设。

### 2.3 对策

| 物品 | 唯一身份从哪来 | 怎么扫 |
|---|---|---|
| **主机 / 控制器** | 原厂序列号（如 `S2000-XL-A-1560`） | 直接扫铭牌 DataMatrix（需 2D 扫码枪） |
| **灯泡 / 消耗品** | **ETIA 自己发号**，入库时分配并打印二维码标签 | 扫 ETIA 自己的码 |

灯泡入库流程（把手写批次的录入次数降到最低）：

```
整箱到货
  ├─ 选型号（Part Number 012-64000R → 对应物料主数据）   ← 每箱一次
  ├─ 录入 Lot Number（手写，人工输一次）                  ← 每箱一次，不是每支
  └─ 输入数量 N → 系统生成 N 个 ETIA 序列号 → 打印 N 张二维码标签 → 逐支贴
```

这样手写批次**一箱只录一次**，出错面最小；每支灯泡拿到自己的 ETIA 身份。

> **贴哪里**：灯泡本体工作时高温，标签贴玻璃/灯体不现实，**贴包装盒**最实际。
> 但客户拆盒装机后盒子可能丢弃 → 链路会断。对策：标签一式两张（一张贴盒、
> 一张做成随附卡片），并且出货单上同时列出序列号，客户凭出货单也能查。

### 2.5 ETIA 序列号与二维码内容规格（一旦印在实物上就不能改）

**序列号格式**

```
E26C-0001482-K
│ │ │    │     └─ 校验位：防止人工念错/输错（如电话报号）
│ │ │    └──────── 7 位流水
│ │ └───────────── 站点：C=中国  T=泰国  V=越南
│ └─────────────── 年份后两位
└───────────────── ETIA 标识,本身就是防伪信号
```

字符集用 **Crockford Base32**（去掉 `I`、`L`、`O`、`U`），从源头避免
`0/O`、`1/I/L` 认错——人工输入和电话报号都会用到。

**二维码内容 = 一条 URL，不是纯序列号**

```
https://www.etiatech.com/v/E26C0001482K?k=7f3a9c2e
```

| 部分 | 作用 |
|---|---|
| 完整 URL | 手机相机扫码**直接打开查询页**，客户不用装 App、不用打字 |
| `/v/` 短路径 | 缩短 URL → 二维码模块数少 → **小标签上也能可靠扫到** |
| `?k=` 签名 | `HMAC-SHA256(序列号, 服务端密钥)` 取前 8 位。**没有实物标签就算不出**，堵死连号遍历（见第 5 节） |

> ⚠️ 密钥一旦泄露，全部已印标签的防伪失效且无法补救。密钥只存服务端环境变量，
> 不进代码库、不进前端、不写进任何文档。

**标签建议规格**：40×20 mm 或 50×25 mm 热敏/热转印不干胶，内容为
二维码 + 人可读序列号 + 型号（`012-64000R`）+ ETIA 标识。
批次号印在标签上属可选——它已经存在数据库里，扫码就能看到。

### 2.6 出库扫码不只是"记一笔",它要能拦错

出货扫描的价值一半在记录,一半在**当场拦住发错货**。每扫一支必须校验:

| 情况 | 系统行为 |
|---|---|
| 这支不属于本张出货单的型号 | ❌ 拒绝,提示应发型号 |
| 这支已经出货给别的客户 | ❌ 拒绝(除非先走退货入库) |
| 这支已被别的订单预留 | ⚠️ 警告,需确认 |
| 已扫数量 < 出货单数量 | 🚫 不允许点"确认发货" |
| 已扫数量 > 出货单数量 | ❌ 拒绝多扫 |

> 没有这一层,扫码只是把纸面记录搬进电脑;有了这一层,它才真正防错。

### 2.4 INTELLI-LAMP：一个可能很值钱的数据源（需向原厂确认）

灯泡标签上印着 **INTELLI-LAMP® TECHNOLOGY**。这是 Excelitas 的技术，
灯泡自带存储、由主机读取，用于记录**实际点灯小时数**。主机背面也能看到
串口（P3），S2000 系列本身支持串口远程控制。

**如果**原厂接口能读出灯泡的标识与累计小时数，那价值远超"扫码记录"：

- 保修可以**按实际点灯小时**判定，而不只是按日期
- 可以在灯泡接近寿命时**主动提醒客户换灯** —— 这是直接的复购生意
- 客户装的到底是不是你们出的那支灯，能对得上

**待确认（建议直接问 Excelitas 技术支持）**：
1. Intelli-Lamp 是否存有**唯一标识**（还是只有小时数）？
2. 能否通过主机串口/接口把它读出来？有没有公开的命令集或 SDK？

在确认之前，**方案不依赖它** —— 按 2.3 的自己发号方案照常推进，
这一条确认可用后作为增强项接入。

## 3. 核心设计：事件流，不是状态字段

**不要**在灯泡表上放一个 `status` 字段反复覆盖——那样历史就没了，
"什么时候入库、什么时候出货"永远答不出来。

正确做法：**一张只追加、永不修改删除的事件表**，当前状态由事件推导。

```
lamp                                lamp_event  (append-only)
├─ serial        唯一               ├─ lamp_id
├─ brand/model                      ├─ seq          该灯泡第几个事件
├─ item_id       → 物料主数据        ├─ event_type
├─ mfg_date      出厂日期            ├─ occurred_at  事件发生时间 (UTC)
├─ mfg_lot       批次               ├─ recorded_at  录入时间 (UTC)
├─ rated_hours   额定寿命            ├─ site_id      哪个站点
├─ warranty_months                  ├─ actor_id     谁扫的
├─ verify_key    HMAC 签名           ├─ ref_type/ref_id  采购单/出货单/工单
└─ (缓存) 当前状态/当前客户           ├─ scan_source  usb_scanner|wecom_scan|manual|import
                                    └─ payload      jsonb（库位、箱号、备注…）
```

**事件类型**

| event_type | 触发 | 关键信息 |
|---|---|---|
| `manufactured` | 供应商数据导入 / 标签解析 | 出厂日期、批次 |
| `received` | **入库扫描** | 采购单、站点、操作人 |
| `stocked` | 上架 | 库位 |
| `reserved` | 预留给订单 | 订单号 |
| `shipped` | **出货扫描** | 出货单、**客户**、目的地 |
| `delivered` | 签收 | 签收日 → **保修起算点** |
| `warranty_claim` | 保修申报 | 故障描述 |
| `returned` / `scrapped` | 退回 / 报废 | 原因 |

> 只追加的好处：任何一次"这灯到底去哪了"的争议，都能拉出完整时间线，
> 而且没人能悄悄改历史。召回时按 `mfg_lot` 一查，去向全出来。

## 4. 扫描录入

### 4.1 入库（批量，速度优先）

仓库场景是**连续扫几十上百支**。最快的不是手机，是**USB 扫码枪**——
它对电脑来说就是键盘，扫一下等于打一串字符加回车。所以：

- 电脑端开一个入库页面，光标停在输入框，扫码枪连扫，每扫一支落一行
- 页面实时显示：已扫数量、与采购单数量的差异、重复扫描告警
- 手机端（企业微信 `wx.scanQRCode`）作为补充，适合零散补录

**必须有的校验**（否则数据会脏）：

| 校验 | 行为 |
|---|---|
| 序列号已存在且已入库 | ❌ 拒绝，提示"重复扫描" |
| 序列号已出货 | ⚠️ 警告，可能是退货，需选择"退货入库" |
| 型号与采购单不符 | ⚠️ 警告，需确认 |
| 数量超出采购单 | ⚠️ 警告，需主管确认 |

### 4.2 出货（准确优先）

出货扫描是**核对**，不是录入：先有出货单，扫描逐支勾对。

- 扫一支 → 系统检查：这支在库吗？型号对得上这张出货单吗？没被别的单占用吧？
- 页面显示"应出 5 支 / 已扫 3 支"，扫够才允许确认发货
- 确认后一次性写入 `shipped` 事件，绑定出货单和客户

### 4.3 离线容错（仓库网络常常不好）

扫描页面在断网时把扫描结果**排进本地队列**，恢复后自动补传。
排队中的扫描在界面上明确标记为"待同步"，绝不假装已经成功。

## 5. 公开查询 —— 这里有个安全问题必须先解决

客户能查是好事，但**直接开放"输序列号看结果"会泄露你们的客户名单**：

> 序列号通常是连号的。任何人（包括竞争对手）写个脚本从 `...001` 遍历到 `...999`，
> 就能拿到"哪些客户、什么时候、买了多少支"——**这等于把销售数据公开**。

### 解决办法：分层 + 签名

**第一层：公开查询（扫码即可，无需登录）**

只回答"这支灯是什么、是不是正品、还在不在保"，**绝不出现客户信息**：

| 显示 | 不显示 |
|---|---|
| ✅ 品牌、型号、额定寿命 | ❌ 客户名称 |
| ✅ 出厂日期、批次 | ❌ 出货地址 |
| ✅ 正品验证：ETIA 正品供应链 | ❌ 价格 |
| ✅ 保修状态：在保 / 过保 / 未激活 | ❌ 经手人、内部单号 |
| ✅ 保修到期日 | ❌ 同批次其他灯泡 |

访问必须带第 2 节说的 HMAC 签名——**只有拿到实物标签的人能查**。
再叠加限流（按 IP / 按序列号前缀），彻底堵死遍历。

**第二层：客户查询（需验证身份）**

客户要看"我买过的所有灯泡、出货单、剩余保修"，就需要验证。
按上次讨论的结论：**不做密码账号，用邮箱魔法链接**——
客户输入邮箱，收到一条链接，点进去看到的**只有出货给这个邮箱所属客户的灯泡**。

> B2B 客户不愿意为查个灯泡注册账号。魔法链接体验最好，你们也不用管密码安全。

**第三层：内部** —— 完整链路、所有事件、所有客户，企业微信免登。

## 6. 部署架构：国内腾讯云 + 境外 Vercel

已定：**国内走腾讯云，国外走 GitHub + Vercel。** 这带来一个必须先回答的问题——
**两套部署，数据放哪一边？**

### 6.1 结论：权威库在国内，境外只放不含客户信息的只读副本

```
        国内 · 腾讯云                        境外 · GitHub + Vercel
┌──────────────────────────────┐      ┌──────────────────────────────┐
│ 内部系统（仓库/销售在用）      │      │ www.etiatech.com/v/<serial>  │
│  · 入库录入 + 发号 + 打标签    │      │ 公开验证页（只读）            │
│  · 出货扫描 + 拦错校验         │      │                              │
│  · 企业微信免登                │      │                              │
├──────────────────────────────┤ 单向 ├──────────────────────────────┤
│ Postgres —— 权威库             │ ───▶ │ 只读副本                      │
│ 全部字段：客户、地址、价格、    │ 脱敏 │ 只有：型号、出厂日、保修状态   │
│ 经手人、内部单号               │      │ **没有任何客户数据**           │
└──────────────────────────────┘      └──────────────────────────────┘
```

**为什么是这个方向：**

1. **写操作都发生在国内** —— 扫码入库、扫码出货都在国内仓库。权威库跟着写操作走，
   延迟最低、最不容易出并发问题。
2. **客户数据不出境** —— 同步只推公开层需要的字段。境外那份副本里根本没有客户名、
   地址、价格，**就算被攻破也泄露不了客户名单**。这既是合规要求，也顺带把第 5 节
   的分层从"靠代码控制"变成"物理上就没有"。
3. **境外部署不需要写权限** —— 公开验证页只读。它连不上权威库，也就不可能被用来
   改数据。

### 6.2 内部系统绝对不能放 Vercel

这一条是硬约束：**Vercel 在国内访问慢且不稳定**。仓库工人连扫五十支灯，
只要卡一下整个流程就废了，工人会立刻退回用纸笔——系统就白做了。

所以：**内部扫描系统只部署在腾讯云。** 境外那套只承载公开验证页。

### 6.3 代码怎么分

公开验证页和内部系统对安全边界的要求完全不同，最干净的做法是**分开**：

| 部署 | 承载 | 代码 |
|---|---|---|
| Vercel（境外） | 官网 + 公开验证页 `/v/[serial]` | 现有 `etiatech-website` 仓库 |
| 腾讯云（国内） | 内部 ops 系统 | **独立仓库**（待建） |

分仓库的理由不是洁癖：**境外那份代码里根本不存在入库、出货、客户查询这些
功能**，不是靠鉴权把它们藏起来。攻击面小一个数量级。

两边共用的只有一小块纯逻辑（序列号生成/校验/签名），已经写成
`lib/traceability/serial.ts`，无外部依赖，可以直接复制或抽成私有包。

> **第 1、2 期全部是内部功能**（入库、发号、打标签、出货扫描），公开验证页排在
> 第 6 期。所以"要不要拆仓库"这个决定**现在不必急着做**，等做到公开页再定即可。

### 6.4 客户在手机上怎么用

「国外网站」和「移动端」不是两套东西，是**同一个响应式页面**：

- 二维码里就是 `https://www.etiatech.com/v/<serial>?k=<签名>`
- 手机相机对着标签一扫 → 直接打开 → 不用装 App、不用打字
- 电脑上也能手动输入序列号 + 标签上的校验码查询

多语言沿用 `DESIGN.md` §3 的方案（英/中/泰/越）。

## 7. 与生产系统的关系

这个模块**不是独立系统**，它就是 `DESIGN.md` 里那套东西的一部分：

- `shipped` 事件的来源就是**出货单扫描**——出货单一确认，灯泡链路自动闭环
- 多站点维度、UTC 时间、通知层可插拔，全部沿用，不另起炉灶
- 将来东南亚开厂，新增一个 site 即可，追溯链路天然覆盖

## 8. 商业设计：让客户一直找 ETIA，而不是直接找原厂

目标定了，功能优先级要跟着变。**单纯的"防伪验证页"锁不住客户——扫一次就走了。**
真正让客户回头的是下面这几件事：

### 8.1 把查询页做成"客户的设备台账"，而不是一次性验证

客户自己通常不记录：这台机器什么时候买的、上次换灯是什么时候、装的哪片滤光片。
**你们记录了，他们就得来查。** 页面要能回答：

- 我公司名下有哪些主机？序列号、滤光片配置、购入日期
- 每台机器换过几次灯？分别什么时候、哪个批次
- 哪支灯还在保？还剩多久

### 8.2 换灯提醒 —— 最直接的复购触发器

灯泡有寿命。系统按出货日 + 预估使用推算到期时间，**赶在客户想起来之前先联系他**。

这是整套系统里**最能直接带来订单的功能**，优先级应该提到很靠前——
比防伪页更靠前。（也正因如此，第 2.4 节 Intelli-Lamp 的实际点灯小时数才那么值钱：
按真实小时提醒，比按日期估算准得多。）

### 8.3 年度校准 —— 已经在收费的复购，只是还没有系统在推

设备每年校准一次，**收费**。这是已经存在的收入，但现在靠人记、靠客户自己想起来。
接进系统后它和换灯提醒是同一类东西，而且更稳定：换灯取决于用量，校准是**按年必到**。

三处联动：

1. **标签上就印着下次校准日期** —— 标签贴在客户设备上，天天被看见。到期客户
   自然会打电话过来。这是整套方案里成本最低的销售动作：一张已经要贴的标签，
   多印一行字。
2. **到期前系统提醒销售** —— 不用等客户想起来。
3. **校准记录挂在序列号下** —— 客户要查「上次校准是什么时候、证书编号多少」，
   只能来找你们。审计和客户自己的质量体系都要这个。

> 还没做过校准的设备，标签上那块位置印的不是空白，而是「年度校准 · 尚未预约」——
> 把空状态变成邀约。

### 8.4 服务记录挂在序列号下

维修、校准、上门、应用调试，全部挂到设备序列号下。客户想查"这台机器修过什么、
调过什么参数"，只能来找你们。**这是原厂给不了的——原厂不知道客户现场发生过什么，
你们知道。**

### 8.5 配置感知的配件推荐

知道客户用的是 S2000-XLA + 320–500 nm 滤光片，就知道他迟早需要哪种导光棒、
辐照度计、备用灯。推荐可以具体到型号，而不是群发广告。

### 8.6 三条边界，别做过头

**① 靠"好用"留人，不能靠"扣数据"留人。**
客户台账必须**随时可导出**。让客户觉得"我的数据被你们扣着"会把人推走；
让他觉得"离开你们就丢了三年的维护历史"才是可持续的粘性。

**② 不要在验证页上遮蔽或弱化 Excelitas —— 应该反着来。**
页面明确显示「Excelitas 原厂制造 · ETIA 授权供应」。原厂品牌是**你们的背书**，
真正的共同敌人是假货和翻新货，不是原厂。遮遮掩掩反而显得可疑，
也会削弱"正品验证"这件事本身的说服力。

**③ 真正的护城河不是序列号本身。**
原厂将来也可能推自己的客户门户。到那天序列号数据不再稀缺，
**但"换灯提醒 + 现场服务记录 + 应用 know-how"仍然只有你们有。**
所以资源要压在 8.2、8.3 和 8.4，而不是把防伪页做得多花哨。

## 9. 分期

按第 8 节的商业目标重排后的优先级 —— **换灯提醒提前，防伪页后置**：

| 期 | 内容 | 能验证什么 |
|---|---|---|
| **1** | 灯泡/设备表 + 事件表 + 入库录入 + **序列号生成与标签打印** | 数据开始积累,实物开始带码 |
| **2** | **出货扫描**(含第 2.6 节的拦错校验)+ 绑定出货单/客户 | **全链路打通**,且当场防发错货 |
| **3** | **换灯提醒 + 年度校准提醒 + 保修到期提醒** | 🔥 直接带来复购订单 |
| **4** | 客户设备台账(邮箱魔法链接登录,可导出) | 客户开始习惯来你们这里查 |
| **5** | 服务记录挂到序列号(维修/上门/应用调试)+ 校准证书 | 原厂给不了的差异化 |
| **6** | 公开防伪验证页 | 销售武器,东南亚打假货 |
| **7** | 批次召回查询、窜货告警、配件推荐、报表 | 管理与销售闭环 |

> 第 2 期完成时,"什么时候生产、入库、出货给谁"就完整了。
> 第 3 期是**商业上回报最快的一期**,建议不要往后拖。
> 第 1、2 期可以先跑起来,不必等 Excelitas 的答复。
