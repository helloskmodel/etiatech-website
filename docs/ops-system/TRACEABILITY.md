# 灯泡序列号全链路追溯 — 设计方案

> 状态：方案草案，待确认
> 关联：`docs/ops-system/DESIGN.md`（生产计划 & 出货管理系统）
> 最后更新：2026-09-07

---

## 1. 需求与价值

**要做的事**：每支灯泡有唯一序列号（"身份证"）。进货扫一次、出货扫一次，
从此每支灯泡都能回答：**什么时候生产 → 什么时候入库 → 什么时候出货给谁**。
客户在网站上可以查询。

投放两处：**海外网站**（etiatech.com）+ **手机端**。

**这件事真正值钱的地方，不止是"有记录"：**

| 价值 | 说明 |
|---|---|
| **防伪** | UV 灯泡在东南亚有假货和翻新货。客户扫码即可验证是不是 ETIA 正品供应链出来的——这是**销售武器**，不只是内部管理 |
| **保修自动判定** | 保修从出货日算起。有了链路，"这支还在保吗"由系统回答，不用翻单据吵架 |
| **窜货/串货追踪** | 泰国的货出现在越南客户手里，一扫就知道 |
| **召回定位** | 某批次有问题，一次查询就能列出这批灯泡去了哪些客户 |
| **客户信任** | 客户能自查自己买的每一支灯，这在 B2B 里是明显的专业度信号 |

## 2. 第一个必须先定的问题：灯泡上的"身份证"长什么样

**这决定了「扫描自动录入」能不能成立。** 三种情况差别极大：

| 标签形式 | 能否直接扫 | 对策 |
|---|---|---|
| 二维码 / DataMatrix | ✅ 直接扫 | 最理想 |
| 一维条码（Code128 等） | ✅ 直接扫 | 需确认码制与是否含前后缀 |
| **只有印刷文字，没有码** | ❌ 扫不了 | 见下方推荐方案 |

灯泡标签面积小，很多原厂只印**文字序列号**，没有条码。如果是这种情况，
"扫描"要靠手机 OCR——可行，但慢、会认错（`0/O`、`1/I`、`8/B`）。

### 推荐方案：入库时由 ETIA 补贴一张自己的二维码标签

这一步同时解决三个问题，强烈建议采纳：

1. **可扫**——不管原厂标签是什么形式，ETIA 的码一定可扫
2. **防枚举**（见第 5 节，这是公开查询的安全命门）
3. **可承载 URL**——手机相机直接扫码就跳转到查询页，客户不用装任何 App

二维码内容就是一条 URL：

```
https://www.etiatech.com/verify/<serial>?k=<签名>
```

`<签名>` 是用服务端密钥对序列号做 HMAC 后取前 8 位。**没有实物标签的人算不出签名，
也就查不了别人的灯**。原厂序列号仍然照常录入并保存，两者一一对应。

> 一次性成本：一台标签打印机 + 入库时贴一张。换来的是可扫、防伪、防枚举。

## 3. 核心设计：事件流，不是状态字段

**不要**在灯泡表上放一个 `status` 字段反复覆盖——那样历史就没了，
"什么时候入库、什么时候出货"永远答不出来。

正确做法：**一张只追加、永不修改删除的事件表**，当前状态由事件推导。

```
lamp                                lamp_event  (append-only)
├─ serial        唯一               ├─ lamp_id
├─ brand/model                      ├─ seq          该灯泡第几个事件
├─ item_id       → 物料主数据        ├─ event_type
├─ mfg_date      出厂日期            ├─ occurred_at  事件发生时间 (UTC)
├─ mfg_lot       批次               ├─ recorded_at  录入时间 (UTC)
├─ rated_hours   额定寿命            ├─ site_id      哪个站点
├─ warranty_months                  ├─ actor_id     谁扫的
├─ verify_key    HMAC 签名           ├─ ref_type/ref_id  采购单/出货单/工单
└─ (缓存) 当前状态/当前客户           ├─ scan_source  usb_scanner|wecom_scan|manual|import
                                    └─ payload      jsonb（库位、箱号、备注…）
```

**事件类型**

| event_type | 触发 | 关键信息 |
|---|---|---|
| `manufactured` | 供应商数据导入 / 标签解析 | 出厂日期、批次 |
| `received` | **入库扫描** | 采购单、站点、操作人 |
| `stocked` | 上架 | 库位 |
| `reserved` | 预留给订单 | 订单号 |
| `shipped` | **出货扫描** | 出货单、**客户**、目的地 |
| `delivered` | 签收 | 签收日 → **保修起算点** |
| `warranty_claim` | 保修申报 | 故障描述 |
| `returned` / `scrapped` | 退回 / 报废 | 原因 |

> 只追加的好处：任何一次"这灯到底去哪了"的争议，都能拉出完整时间线，
> 而且没人能悄悄改历史。召回时按 `mfg_lot` 一查，去向全出来。

## 4. 扫描录入

### 4.1 入库（批量，速度优先）

仓库场景是**连续扫几十上百支**。最快的不是手机，是**USB 扫码枪**——
它对电脑来说就是键盘，扫一下等于打一串字符加回车。所以：

- 电脑端开一个入库页面，光标停在输入框，扫码枪连扫，每扫一支落一行
- 页面实时显示：已扫数量、与采购单数量的差异、重复扫描告警
- 手机端（企业微信 `wx.scanQRCode`）作为补充，适合零散补录

**必须有的校验**（否则数据会脏）：

| 校验 | 行为 |
|---|---|
| 序列号已存在且已入库 | ❌ 拒绝，提示"重复扫描" |
| 序列号已出货 | ⚠️ 警告，可能是退货，需选择"退货入库" |
| 型号与采购单不符 | ⚠️ 警告，需确认 |
| 数量超出采购单 | ⚠️ 警告，需主管确认 |

### 4.2 出货（准确优先）

出货扫描是**核对**，不是录入：先有出货单，扫描逐支勾对。

- 扫一支 → 系统检查：这支在库吗？型号对得上这张出货单吗？没被别的单占用吧？
- 页面显示"应出 5 支 / 已扫 3 支"，扫够才允许确认发货
- 确认后一次性写入 `shipped` 事件，绑定出货单和客户

### 4.3 离线容错（仓库网络常常不好）

扫描页面在断网时把扫描结果**排进本地队列**，恢复后自动补传。
排队中的扫描在界面上明确标记为"待同步"，绝不假装已经成功。

## 5. 公开查询 —— 这里有个安全问题必须先解决

客户能查是好事，但**直接开放"输序列号看结果"会泄露你们的客户名单**：

> 序列号通常是连号的。任何人（包括竞争对手）写个脚本从 `...001` 遍历到 `...999`，
> 就能拿到"哪些客户、什么时候、买了多少支"——**这等于把销售数据公开**。

### 解决办法：分层 + 签名

**第一层：公开查询（扫码即可，无需登录）**

只回答"这支灯是什么、是不是正品、还在不在保"，**绝不出现客户信息**：

| 显示 | 不显示 |
|---|---|
| ✅ 品牌、型号、额定寿命 | ❌ 客户名称 |
| ✅ 出厂日期、批次 | ❌ 出货地址 |
| ✅ 正品验证：ETIA 正品供应链 | ❌ 价格 |
| ✅ 保修状态：在保 / 过保 / 未激活 | ❌ 经手人、内部单号 |
| ✅ 保修到期日 | ❌ 同批次其他灯泡 |

访问必须带第 2 节说的 HMAC 签名——**只有拿到实物标签的人能查**。
再叠加限流（按 IP / 按序列号前缀），彻底堵死遍历。

**第二层：客户查询（需验证身份）**

客户要看"我买过的所有灯泡、出货单、剩余保修"，就需要验证。
按上次讨论的结论：**不做密码账号，用邮箱魔法链接**——
客户输入邮箱，收到一条链接，点进去看到的**只有出货给这个邮箱所属客户的灯泡**。

> B2B 客户不愿意为查个灯泡注册账号。魔法链接体验最好，你们也不用管密码安全。

**第三层：内部** —— 完整链路、所有事件、所有客户，企业微信免登。

## 6. 两个投放点

你说要放"国外网站"和"移动端"——其实**是同一个页面**，不需要做两套：

```
                    ┌─────────────────────────────┐
   手机相机扫码  ──→ │  /verify/<serial>?k=<签名>   │ ←── 网站导航入口
   （无需装 App）    │  响应式页面，手机/电脑同一套   │     （手动输序列号 + 校验码）
                    └─────────────────────────────┘
```

- **海外网站**：`etiatech.com/verify` —— 英文优先，按 `DESIGN.md` 的多语言方案支持中/泰/越
- **移动端**：同一个 URL。二维码本身就是这个链接，手机相机一扫直接打开
- **内部扫描页不放在公开网站上**，走企业微信内的 H5，与公网入口分开

## 7. 与生产系统的关系

这个模块**不是独立系统**，它就是 `DESIGN.md` 里那套东西的一部分：

- `shipped` 事件的来源就是**出货单扫描**——出货单一确认，灯泡链路自动闭环
- 多站点维度、UTC 时间、通知层可插拔，全部沿用，不另起炉灶
- 将来东南亚开厂，新增一个 site 即可，追溯链路天然覆盖

## 8. 分期

| 期 | 内容 | 能验证什么 |
|---|---|---|
| **1** | 灯泡表 + 事件表 + 入库扫描（电脑端 + 扫码枪） | 入库数据开始积累 |
| **2** | 标签打印（含签名二维码）+ 公开查询页 | 客户能扫码验真伪 |
| **3** | 出货扫描 + 绑定出货单/客户 | **全链路打通** |
| **4** | 保修自动判定 + 到期提醒 | 保修不再靠翻单据 |
| **5** | 客户邮箱魔法链接，查自己的灯泡 | 客户自助 |
| **6** | 批次召回查询、窜货告警、报表 | 管理闭环 |

> 第 3 期完成时，你要的"什么时候生产、入库、出货给谁"就完整了。
> 第 1、2 期可以先跑起来，不必等出货模块。

## 9. 待确认

| # | 事项 | 为什么关键 |
|---|---|---|
| 1 | **灯泡上现在到底印的是什么？**（二维码 / 条码 / 纯文字）最好拍一张标签照片 | 决定能否直接扫，以及要不要补贴自己的标签 |
| 2 | 原厂能否提供**出厂日期、批次**的电子清单（Excel/接口）？ | 没有的话"什么时候生产"只能靠标签上印的信息 |
| 3 | 保修期怎么算：按**出货日**还是**签收日**？多少个月？是否按点灯小时数？ | 决定保修判定逻辑 |
| 4 | 一支灯泡会不会**退回再出货**给另一个客户？ | 决定事件流是否允许回到在库状态 |
| 5 | 入库量级：一次进货几十支还是几百支？ | 决定扫码枪 vs 手机，以及是否需要批量导入 |
| 6 | 公开查询页要不要显示**客户自己的名字**（客户扫自己的灯时）？ | 涉及是否必须先验证身份 |
